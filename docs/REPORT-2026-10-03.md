## What the lesson teaches
- A static export of a Next.js site and why it fits a personal site.
- Two languages done properly: one root layout per language so `<html lang>` is
  right, every string in a dictionary, `hreflang` and canonical URLs, a shared
  type scale.
- Japanese line breaks: splitting copy into phrases so no line ends on a lone
  character.
- Deploying to GitHub Pages with Actions, the base-path trap
  (`user.github.io/repo/` vs a custom domain) and how the workflow avoids it.
- A Content-Security-Policy without server headers (`<meta http-equiv>`), and
  why `upgrade-insecure-requests` broke the site before HTTPS was ready.
- Debugging stale deploys: caches, and reading the build log to prove what ran.
- A short exercise for students at the end.

## How the Japanese and Portuguese versions will arrive
`.github/workflows/translate-content.yml` runs on a push to `master` that
touches `content/**.md` or `content/*.yaml` (and on manual dispatch). It runs
`scripts/translate_content.py`, which writes a sibling only when it is missing
or empty, so after this branch is merged to `master` it will create
`content/tech/t40.ja.md` and `t40.pt.md` (stamped with `source_sha`), rebuild
`docs/`, push a branch `auto/translations-<run id>` and open a PR (or, if
Actions may not open PRs, print a compare link in the run summary). That PR has
to be merged by a person. Until then the `ja` and `pt` T40 pages and list
entries show the English text (the builder falls back to English). Needs the
`GEMINI_API_KEY` secret; if the translator fails, the workflow's last step
fails the run naming the missing files.
